### Goals

Turn the gateway into a deployable production candidate by adding a minimal production HTTP runtime, containerization, non-root execution, explicit production configuration, and a final verification checklist. Provider expansion remains separate from production hardening.

### Completed

- Added `src/server.ts` as a minimal Node.js HTTP runtime around the provider-neutral HTTP handler.
- Added mandatory `GATEWAY_API_KEY` startup configuration for the standalone server.
- Added configurable `PORT` with default `3000`.
- Added `Dockerfile` with a multi-stage Node 20 Alpine build.
- Build stage executes the complete `npm test` suite before producing the runtime image.
- Runtime image copies only the compiled application and package metadata.
- Runtime container runs as the non-root `node` user.
- Runtime exposes port `3000`.
- Added production `NODE_ENV=production` configuration.
- Kept secrets outside the image; the API key is supplied through environment configuration at runtime.
- Updated `plan.md` with Phase 18 production-readiness boundaries.

### Deployment flow

```text
Source
  ↓
Docker build
  ↓

  ↓

  ↓

  ↓

  ↓
GATEWAY_API_KEY supplied at runtime
  ↓
HTTP server :3000
```

### Production-readiness checklist

- [x] TypeScript build is part of `npm test`.
- [x] Complete test suite is part of the container build.
- [x] Runtime image does not contain source/test files from the build stage.
- [x] Runtime executes as non-root.
- [x] API key is runtime configuration, not an image constant.
- [x] HTTP API has request authentication and size validation.
- [x] Request IDs are propagated/generated by the HTTP boundary.
- [x] Provider credentials remain outside the HTTP response contract.
- [ ] CI green for the final Phase 18 commits.
- [ ] Live Redis integration test.
- [ ] Live provider contract tests.
- [ ] Container image vulnerability scan.
- [ ] Load/concurrency test in a deployment-like environment.
- [ ] Secret scan of repository history.
- [ ] Production deployment smoke test.

### Important limitation

Phase 18 is intentionally a production-candidate baseline, not a claim of production certification. The final unchecked items require an actual CI/deployment environment and external service integrations. In particular, the standalone `src/server.ts` currently initializes an empty provider configuration; a real deployment must inject the actual gateway configuration, adapters and credential store before serving traffic.

# Definition of Done for Every Phase

Before marking a phase complete:

- Implementation is committed.
- Tests for the phase are added.
- Existing tests still pass.
- No secrets are introduced.
- Documentation is updated.
- Provider-neutral architecture is preserved.
- No provider policy or quota is bypassed.
- The phase's exit criteria are explicitly verified.

# Working Rule

Implement **one phase at a time**. Do not prematurely implement later-phase infrastructure merely because the architecture anticipates it.

When starting a phase, first review the current repository state, identify the exact gap, implement only that phase, run the relevant tests, update this plan's status, and then commit the result.
